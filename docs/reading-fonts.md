# Reading fonts on the stock `xteink_app`: the list is open, here is the recipe

Session 2026-09-07 (the "rfont" squad task). Question: can the stock's *reading* font list be extended
with a font we supply? **Yes — proven end to end in the emulator on 7.2.4.** Drop an `.xtf` (the same
v2 format `tools/xtfont.py` writes for the system font, at any cell size) or a raw `.bin` bitmap font
into `/fonts/` on the card; the reader's Font picker lists it by file name and renders the book in it.
No patch, no signature, no manifest, no install step. Everything below says how it was established;
numbers marked *(unverified)* were read from the binary and not exercised.

All code addresses are **7.2.4** (`images/device/stock-app0-7.2.4.bin`, `tools/ghidra_stock.py`
exports in `images/ghidra/stock-7.2.4/`). 7.5.4 was only string-checked (§7). Screenshots live in the
session scratch directory `/private/tmp/claude-501/-Users-mini-xteink-x4/a746b33c-5073-40dc-bf8c-628f1fad9f27/scratchpad/rfont/`
(referred to as `$S` below); they are not in the repository and are regenerated by §5.

## 0. The answer in one paragraph

The reader has its own font provider pair, `Domain::Reading::Font::{XtfFontProvider, BinFontProvider}`,
behind a picker (`Views::ReadingFontPickerLayerPresenter`). The picker's list builder
(FUN_42145bd0) adds the two system cells first — labelled **System Font Small / System Font Medium**
— then walks **`/sdcard/fonts`** and **`/sdcard/Pushed Fonts`** for files ending in **`.xtf`** or
**`.bin`** (FUN_4205d3ac with the extension filters at `s_system_small_xtf_3c38ebea+0xc` = ".xtf" and
`DAT_3c38a887` = ".bin"), keeps up to **64** entries of (file name, full path), no header probe at scan
time, no signature. Selecting an entry opens the file through the provider matching its extension.
Both providers draw **pre-rendered 1-bpp bitmaps** at the file's own cell size: there is no scaling and
no outline rasteriser (the app has no FreeType), so a reading font is one file per size, exactly like
the UI font, and its quality is whatever the converter puts in the cells. The emulator's page renders
are pure black/white (two grey levels used in every reader screenshot, measured with PIL) — the
"anti-aliased reader path" assumed in `docs/fonts.md` §0 does not exist for these fonts.

## 1. What the picker lists on a stock boot

Boot of `flash-2026-09-06-a.bin` (net_en 0) with the device's card mirror plus `tests/mkepub.py`'s
book (§5 has the commands). Home → hamburger (88,38) → All Files (245,150) → the book → page centre
(400,240) opens the reading menu: Contents / Progress / **Font** / More (`$S/05-readingmenu.png`).
**Font** (landscape 740,185) opens a panel with a **"Font — system_medium"** card and Paragraph 1.2x /
Line Spacing 1.0x / Page Margin 2.0x steppers (`$S/06-fontpicker.png`); there is **no font-size
control** anywhere (More = Bluetooth / Auto Flip / Lock Touch / Advanced, `$S/09-more.png`). Tapping
the card (555,340) opens the picker: **"2 fonts": System Font Medium (selected), System Font Small**
(`$S/07-fontlist.png`). Those are the card's `XTData/system_fonts/misans-demibold/system_medium.xtf`
(24×24) and `system_small.xtf` (20×20) — the reader reaches the system font through a
`ReadingFontBackendRouter::SystemBodyProvider` (typeinfo 0x3c3d52a4; the list builder names the
entries `system_small`/`system_body`, and FUN_42118d54's default selection is `system_body`). So on
the device today the *only* reading sizes are the two UI cells; "font size" in this reader means
"which cell", which is why the list is the lever.

## 2. Where the reader scans, and how the list is built (evidence)

Strings and their code references (`ghidra_stock.py xrefs`):

| string | DROM | read by |
|---|---|---|
| `/sdcard/fonts` | 0x3c3de555 | FUN_42145bd0 (picker list, ×2), FUN_421493bc (second list, ×2), FUN_421c502c (cloud/file-push path classifier) |
| `/sdcard/Pushed Fonts` | 0x3c3de540 | the same three, plus FUN_421c5554/FUN_421c5774 (push classifier) |
| `/fonts/` + `.xtf,.bin` | 0x3c38a850, 0x3c38a882 | literal pool 0x42043b18/20 in the code gap after FUN_42042248 (Ghidra made no function there); the string run `/picture/`, `/wallpapers/`, `/fonts/`, `.bmp,…`, `.xtf,.bin`, `/XTApps/` next to the "XTEink Files" HTML page reads as the WiFi file server's upload targets and their accepted extensions *(inferred from the neighbourhood, not traced)* |
| `font.xtf.open` / `font.bin.open` | 0x3c38f41f / 0x3c38f568 | FUN_4210fc44 (XtfFontProvider open), FUN_42112fd4 (BinFontProvider open) |
| `[XtFontCache] …` | 0x3c38f0xx | the `.xtf` header parser's log lines (printed on the console when a font opens, §3.1) |

`FUN_42145bd0` (438 B, called from the picker presenter's init FUN_42145db4): clears a 64-entry table
(names at +0x70 stride 0x60, paths at +0x1870 stride 0x140), adds `system_small` and `system_body`
with the pack labels 0x1f/0x1e ("System Font Small/Medium"), then — only if the card is mounted
(FUN_4205c678) — calls the directory walker `FUN_4205d3ac(vfs, dir, ext, callback)` four times:
(`/sdcard/fonts`, ".xtf"), (`/sdcard/fonts`, ".bin"), (`/sdcard/Pushed Fonts`, ".xtf"),
(`/sdcard/Pushed Fonts`, ".bin"). The walker `opendir`s, skips dot-files, `stat`s each entry, filters
by the suffix (FUN_4205cac4), and hands (name, path) to the callback FUN_42145638 → FUN_421455a4,
which de-duplicates by path and appends while the count is < 0x40. **Nothing opens or validates the
file at scan time.** The current selection is matched against the entry *names* with a
case-insensitive strcmp (FUN_42148a64) — the name comes from FUN_42118d54, which reads the reading
settings (defaults `system_body`, paragraph 1.2f, line 1.0f) — so an entry is identified by its file
name, not its path. Sub-directories are not walked. Where the selection is persisted (per book or
global, NVS or card) was not chased *(unverified)*; after a reboot the reader reopened the book in
the last font it could load, and the picker highlight did not always agree with the page (§4).

The second list builder FUN_421493bc (same directories, no system entries, sorted by
FUN_42148cb0) belongs to the **External Font Management** layer ("No external fonts", "Delete %u
selected fonts?", "%d fonts" — toast-pack strings, so no xrefs); it manages the same files.

## 3. The two formats and how they are told apart

By extension only: `.xtf` → XtfFontProvider, `.bin` → BinFontProvider (the `.bin` name parser also
refuses anything not ending in `.bin`, case-insensitively).

### 3.1 `.xtf` — the system-font format, any cell size

The reader's open routine (FUN_4210fc44, "font.xtf.open") opens the file "rb", takes a 32 KiB
scratch arena (`reading.font.xtf.scratch`), and hands the header to the same `XtFontCache` parser
the system font uses (its log lines are `[XtFontCache] …`, in Chinese). For the package built in §5
the console printed:

```
[XtFontCache] 已解析头部 v2.0 cell=24x24 layout(full=24 ascii=13) ascii_tbl(off=112 cnt=95) bpg=76 flags=0x03 metrics=2 range_cnt=3 glyph_cnt=526
[XtFontCache] 命中外部映射索引
[XtFontCache] range/sparse 使用外部映射索引 (省 RAM ~48 B)
[XtFontCache] cp-hash 启用 cap=32768 slots=13797
[XtFontCache] 已打开 /sdcard/fonts/CharisBold24.xtf  slots=13797
```

("parsed header … / external mapping index hit / range/sparse uses the external index / cp-hash on /
opened …"). That line also names two header bytes `tools/xtfont.py` copies blind: **byte 0x0d is
`layout full` (the full-width cell) and byte 0x0e is `layout ascii` (the half-width ASCII cell, 13 for
24, 11 for 20, 17 accepted for 32)**, and the u16 at 0x08 is printed as `flags=0x03` *(all three
inferred from the printed values equalling the stored bytes, not from the parser's code)*. The same header
at **cell 32×32** (record size 132) was parsed and opened identically (`$S/20-after-select-charis32.png`,
console `cell=32x32 layout(full=32 ascii=17) … bpg=132`), so the reader does **not** pin the cell to
20/24; the cp-hash capacity dropped from 32768 to 16384 slots for the bigger cell (a RAM budget,
`0xc000`/`0x60000`-style constants also appear in the `.bin` opener), which is the only size-dependent
behaviour seen. The CRC-32 words at 0x30/0x34 are written by `xtfont.py`; whether the reader checks
them was not tested (they were always right) *(unverified)*. The maximum cell the reader accepts and
the meaning of `metrics=2` were not probed *(unverified)*. Opening an external `.xtf` writes a
sidecar cache on the card: after the test the image held `XTCache/fontpre/b20b93e6.xtfp` (7,332 B)
and `01bd174d.xtfp` (12,652 B), one per `.xtf` opened (the `%s/%08x.xtfp` / `font.xtf.sidecar.save`
strings; the directory is created by FUN_42110b74, which also deletes stale `.base.xtfp`-suffixed
files there). Nothing needs to be shipped for it — the reader makes it — and the `.bin` left no file.

### 3.2 `.bin` — a raw, flat, codepoint-indexed bitmap array

Reverse-engineered from FUN_42112fd4 (open), FUN_421ec598 (name parser), FUN_421ec774 (validator,
`appdis.py` — the SLEIGH stops on it), FUN_421ec758/FUN_421ec7c8 (sizes), FUN_421ec7e0 (pixel test),
FUN_421ec824 (advance derivation), FUN_4235f1ac (index), and confirmed by two boots:

* **Cell size comes from the file name**, not from a header — there is no header at all. The parser
  requires the `.bin` suffix, then finds the *last* `×` (U+00D7, `DAT_3c48fdee`), `x` (`0x3c396520`)
  or `X` (`0x3c398988`) in the base name with **two decimal digits immediately before and after**:
  `<anything>WWxHH.bin`, e.g. `PTFull32x32.bin` → W=32, H=32. FUN_421ec774 then requires
  **10 ≤ W ≤ 98 and 10 ≤ H ≤ 98** (`addi −10 … movi 89` range checks).
* **Bytes per glyph** `bpg = ceil(W/8) × H` (FUN_421ec758), rows top-down, **MSB first, 1 = ink**
  (FUN_421ec7e0 tests `0x80 >> (x & 7)` in row `y*stride`).
* **Glyph index = the Unicode codepoint** (FUN_4235f1ac stores the codepoint as a u16 and refuses
  D800–DFFF; FUN_421ec7c8 gives offset = index × bpg). Nothing else is in the file: no metrics, no
  ranges, no kerning.
* **The file size must be exactly 65536 × bpg** — FUN_421ec774's tail compares `bpg << 16` (as a
  64-bit value) with the 64-bit file size obtained by `ftell` at open. A 32 KiB file holding only
  U+0000–U+00FF was refused: the reader toasted **"Font load failed. Switched to default font."**
  (`$S/21-after-select-bin.png`). The same glyphs in an **8 MiB** file (32×32 → 128 B × 65536, blank
  outside Latin) loaded silently and rendered the page (`$S/26-after-select-ptfull.png`).
* At open the 95 ASCII cells (seek `0x20 × bpg`, read `0x5f × bpg`) are kept in RAM and each cell is
  scanned for its ink columns: **advance = max_col − min_col + 1, x_offset = −min_col**; a blank cell
  (space) advances `max(W/2, 1)` (FUN_4235f1f8). Other codepoints are read on demand into an LRU
  cache sized from `0xc000/bpg` and `0x60000/bpg` *(unverified sizing)*. So a `.bin` is proportional,
  but its spacing is the ink box plus whatever the layout adds — no side bearings, no kerning.

This is the classic "HZK"-style Chinese raw bitmap font generalised to Unicode: the format you get
from any "TTF → C array / .bin dot-matrix font" tool once the file is padded to the full BMP.

## 4. Rendering: bitmaps, no scaling, one file per size

* Selecting **CharisBold24.xtf** re-rendered the page live in Charis SIL Bold at the 24 cell
  (`$S/19-after-select-charis24.png`; the picker stays open with the entry highlighted). Selecting
  **CharisBold32.xtf** rendered it bigger with a wider line pitch (`$S/20-…`), so the line box follows
  the file (which header field — `advance_y`, line height or the cell — was not isolated
  *(unverified)*). Selecting **PTFull32x32.bin** rendered PT Sans Bold with the ink-derived advances
  (`$S/26-…`; justified lines, visibly looser word spacing than the `.xtf`). Side by side at 2×:
  `$S/22-zoom-system-vs-bin-vs-charis32.png` (top: the stock MiSans 24; middle: the fallback after
  the failed 32 KiB `.bin`; bottom: Charis 32).
* Every reader screenshot uses exactly the grey levels {0, 255}: the reader draws 1-bpp cells
  (`Domain::Reading::Render::BitmapGlyphRenderer`), no anti-aliasing, no scaling. Quality is capped
  by the converter's rasterisation at the cell size, exactly as for the UI font, and a family needs
  one file per size the user should be able to pick — the picker *is* the size control.
* The **fallback** after a failed load ("Switched to default font") is a rounded sans at roughly a
  28–32 px cell that is **not** the card's system font (larger than the 24-px MiSans) and survived a
  reboot with the failed selection persisted (`$S/24-reader3.png`). Its source was not pinned
  *(unverified)*: 7.2.4's DROM holds one embedded `.xtf` (0x3c3fc608, 16×16, 14 glyphs — a symbol
  set, not this), two U8g2 fallback fonts (`docs/stock-firmware.md` §4) and the compressed blocks the
  survey flagged; 7.5.4's DROM embeds **four** `.xtf` headers (16×16, 20×20, 24×24 and a 36×36 with
  `advance_y` 45 at file 0xaca28) — the built-in reading font is probably one of those there.

## 5. The recipe (proven on 7.2.4 in the emulator)

1. Build the font. Cell 24 works with the tool as it is; other cells need a header profile
   (`xtfont.py` refuses cells other than 20/24 by design, because the copied header bytes were only
   read off the card's two files). The scratch script that made the test fonts, verbatim (kept at
   `$S/build_fonts.py`; the 8 MiB `.bin` variant is the same loop over `bytearray(bpg * 0x10000)`):

   ```python
   import sys; sys.path.insert(0, 'tools')
   from xtfont import build_xtf, select_codepoints, CELL_PROFILE
   cps = {cp for cp in select_codepoints('CharisSIL-Bold.ttf') if cp < 0x250}   # Latin, fast
   open('CharisBold24.xtf', 'wb').write(build_xtf('CharisSIL-Bold.ttf', 24, cps, size=20)[0])
   CELL_PROFILE[32] = {'unk06': 0x140, 'unk08': 3, 'advance_y': 30, 'byte0d': 32, 'unk0e': 17,
                       'unk0f': 2, 'line_height': 35, 'descent': -9, 'baseline': 26}   # accepted
   open('CharisBold32.xtf', 'wb').write(build_xtf('CharisSIL-Bold.ttf', 32, cps, size=26)[0])
   ```
   For a `.bin`: `W = H = 32; bpg = ((W + 7) // 8) * H; out = bytearray(bpg * 0x10000)`, draw each
   codepoint 1-bpp into its `W×H` cell with the baseline where you want it and OR the rows in at
   `cp * bpg + y * stride`, MSB first; name the file `NameWWxHH.bin`.
2. Put the files in **`/fonts/`** on the card (`/sdcard/Pushed Fonts` works the same; the file
   browser shows the folder with type badges XTF / BIN, `$S/12-reader2.png`). On a card image:
   `mmd -i SD.img@@1048576 ::/fonts; mcopy -i SD.img@@1048576 -o X.xtf ::/fonts/`. On the device:
   USB mass storage, or the WiFi file server's `/fonts/` upload target.
3. Open a book → tap the page centre → **Font** → the **Font** card → the file name. The page
   re-renders at once; nothing restarts. The label is the file name including the extension,
   truncated with an ellipsis after about 14 characters ("PTSansBold32x3…"), so name files for the
   picker.

## 6. What the picker's entries map to on disk

| entry | on disk | provider |
|---|---|---|
| System Font Medium | `XTData/system_fonts/<font_id>/system_medium.xtf` (24×24) via the system runtime | SystemBodyProvider |
| System Font Small | `…/system_small.xtf` (20×20) | SystemBodyProvider |
| `<name>.xtf` | `/sdcard/fonts/<name>.xtf` or `/sdcard/Pushed Fonts/<name>.xtf` | XtfFontProvider |
| `<name>WWxHH.bin` | same directories | BinFontProvider |

A replaced *system* font (`tools/xtfont.py install`) therefore changes the two system entries as well;
the reading list and the UI font are independent otherwise.
